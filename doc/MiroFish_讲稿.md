## 开场(约 30 秒)

各位老师、同学,大家好。

我今天给大家讲解的项目叫 **MiroFish**——一个多智能体社交媒体仿真预测引擎。这份《需求规格说明书》是我作为软件工程课程作业完成的,接下来大约 17 分钟的时间,我会带大家走一遍**从问题背景、到用例建模、到非功能性约束的完整需求工程链路**。

讲解过程中我会把重点放在两件事上——**第一,为什么这么建模;第二,工程上做了哪些取舍**。我尽量不照念文档,而是把每一节背后的设计意图讲清楚。

## 第一部分:这个项目到底在做什么(约 2 分钟)

**[切片:项目一句话定位]**

我先用一句话给项目定位:**MiroFish 是一个把"上传文档 + 自然语言需求"自动转化为"社交媒体推演报告"的引擎**。

我举一个具体场景大家就明白了——

假设一家公司要发布一款新手机,他们想知道:**如果按方案 A 发布,Twitter 和 Reddit 上的网友会怎么反应?哪些子社群会被点燃?品牌情感会朝哪个方向走?**

**[强调]**传统舆情分析工具是回答不了这个问题的——因为它们做的是**回溯**:已经发生的事情拿来分析。而 MiroFish 做的是**前瞻**:还没发生的事情,我先在虚拟空间里模拟一遍给你看。

实现思路也很直接:用大语言模型抽取本体、构建知识图谱、生成虚拟用户人设,再调用 CAMEL-AI 团队开源的 OASIS 框架,在 Twitter 和 Reddit 两个虚拟环境里跑出一份预测报告。整个流程对用户来说是**五步**:上传文档 → 构建图谱 → 生成人设 → 运行仿真 → 阅读报告并追问。

请大家记住"**五步流水线**"这个词,后面所有的功能模块、所有的 API 设计,都是围绕它展开的。

## 第二部分:背景与意义(约 3 分钟)

**[切片:第一章 项目背景]**

我们看文档第一章。需求规格说明书最容易写成流水账,所以我在背景这一节用了一种**问题驱动的叙事**——**先讲传统工具的四个局限,再讲 MiroFish 怎么针对性地解决**。

四个局限分别是——

第一,**回溯性而非前瞻性**。这一条最致命,决策者要的是"如果这样做会发生什么",而不是"已经发生了什么"。

第二,**缺少群体动力学建模**。传统工具只看单条文本的情感分,看不到用户之间的转发链路、看不到子社区的演化。

第三,**无法定制化**。通用模型对特定行业、特定话题适配不了。

第四,**报告产出僵化**。固定模板,决策者不能就关键发现进一步追问。

**[停顿]**

这四点为什么重要?**因为它们直接对应了 MiroFish 的四个核心设计决策**——多智能体仿真解决前瞻性、图谱建模解决群体关系、定制化人设解决适配、可对话报告解决追问。

**[强调]**问题和方案是**闭环**的。这是写需求文档的一个关键技巧——**不要孤立地讲你做了什么,要讲你为什么必须这么做**。

意义这一节我分了四层:方法学价值、应用价值、产品价值、技术价值。我特别想提一下**技术价值**——文档里写的是"探索 LLM Agent + 子进程隔离 + 文件 IPC 的工程化模式"。这句话后面会反复出现,因为它是整个系统架构最关键的一个决策。

## 第三部分:功能性需求(约 7 分钟)——这是重头戏

**[切片:第二章 功能性需求]**

第二章是整份文档的核心。我按四个层次来讲:**功能概览 → 用例建模 → 动态行为(顺序图) → 静态结构(类图)**。

### 3.1 功能模块概览(约 1 分钟)

**[切片:F1-F7 功能模块表]**

我把功能拆成了七个模块,F1 到 F7。

这里有一个细节请大家注意——**F1 到 F6 是用户视角的五步流水线,F7 是系统支持类**。

我没有按"前端模块、后端模块、算法模块"这种**技术维度**去拆。**[强调]**因为需求文档的第一读者是产品经理和老师,不是程序员。**功能分解一定要从用户能理解的视角出发**——这是我做这一节时最重要的判断。

### 3.2 用例建模(约 2 分钟)

**[切片:用例图与参与者]**

参与者识别这一节,我特意拎出来讲一个**容易踩的坑**。

我只画了三个 Actor——**用户、LLM 服务、Zep 图谱服务**。**OASIS 仿真引擎和 ReportAgent 我没有画**,虽然它们也是"会执行任务的实体"。

**[停顿]**为什么?

因为 **Actor 的定义是"系统外部的、与系统交互的角色"**,而 OASIS 和 ReportAgent 是系统**内部**的组件——它们是子进程或服务类,不是外部参与者。这是 UML 用例建模里很多同学会混淆的地方,**别把内部模块画成 Actor**。

**[切片:UC6 用例描述]**

三个关键用例描述里,我重点讲 **UC6——启动并监控仿真**。

主流程很标准——用户点击启动、前端发请求、后端 spawn 子进程、前端轮询状态。但请大家看**备选流程**:"端口或资源占用,抛出错误并清理半成品文件"、"用户中途取消,发送 CLOSE_ENV 命令优雅终止"。

**[强调]备选流程才是用例描述的灵魂**。主流程谁都能写,备选流程考验的是你对系统鲁棒性的思考——**异常会怎么发生、发生后系统怎么恢复**。

我给大家一个经验值:**主流程和备选流程的字数比例,最好不要超过 2:1**。否则说明你只想了 happy path,没想 unhappy path。

### 3.3 顺序图——三张图,三种工程模式(约 3 分钟)

**[切片:三张顺序图并排]**

接下来是我最想跟老师重点交流的部分。

文档里画了**三张顺序图**——它们看起来都在描述"用户操作 → 后端调用 → 返回结果",但**本质是三种完全不同的工程模式**。我专门把它们对比着讲。

**[切片:顺序图一]**

**第一张图——图谱构建,用的是"线程 + 任务表轮询"**。

为什么?因为图谱构建耗时几十秒到几分钟,在主线程里同步等待会阻塞整个 Flask 服务。所以后端开一个 daemon Thread 去跑,主线程立刻返回 task_id,前端拿着 task_id 定时轮询进度。**这是中等耗时任务的标准方案**。

**[切片:顺序图二]**

**第二张图——仿真启动与采访,用的是"子进程 + 文件 IPC"**。

仿真为什么不能用线程?**[强调]三个原因**:

第一,OASIS 框架重度使用 asyncio 和第三方库,和 Flask 主线程会冲突;
第二,单次仿真可能跑几十分钟,必须**可以独立 kill**;
第三,仿真结束后子进程不退出,要继续接收 Interview 命令。

所以用子进程做隔离,用文件队列做通信——Flask 把命令 JSON 写到 ipc_commands/ 目录,子进程轮询读取并把结果写回 ipc_responses/。**这是长时运行 + 可中断 + 可追问任务的标准方案**。

**[切片:顺序图三]**

**第三张图——报告生成,用的是"SSE 流式推送"**。

报告是由 LLM 一段一段写出来的,用户希望**边写边看**,而不是等十分钟看到一坨。所以用 Server-Sent Events,后端每生成一段就 push 一段。**这是增量产出任务的标准方案**。

**[停顿,转向老师]**

所以大家看,**为什么这个系统不能用一种通信模式打天下?**

因为任务的耗时特征和交互需求,决定了通信模式。**轮询、IPC、SSE,不是技术偏好,而是任务性质驱动的设计选择**。

这是我想让大家从这三张图里学到的最核心的东西——**画顺序图不是为了画图,是为了暴露系统在不同时间尺度上的行为差异**。

### 3.4 类图(约 1 分钟)

**[切片:分析类图]**

类图我重点指三个东西。

第一,**ProjectStatus 是一个状态枚举**——CREATED 到 ONTOLOGY_GENERATED,到 GRAPH_BUILDING,再到 GRAPH_COMPLETED,任意状态都可能转到 FAILED。**这个状态机是整个项目流程的脊柱**,前端的所有按钮可点不可点,都是看这个状态。

第二,**Simulation 类聚合了 SimulationConfig、AgentProfile、RunState** 三个东西。**"配置 + 人设 + 运行时"的三段式结构**,是仿真类应用的常见建模套路,大家以后做类似项目可以参考。

第三,**SimulationIPCClient 和 IPCCommand 是依赖关系,不是继承**。这反映了文件 IPC 的本质——**Client 不直接调用子进程的方法,而是发命令**。这其实就是设计模式里的**命令模式(Command Pattern)**,在这张图里被显式建模出来了。

## 第四部分:非功能性需求(约 3 分钟)

**[切片:第三章 NFR 表格]**

非功能性需求一共 15 条,我不一条条念,**挑四条最能体现工程取舍的讲**。

**[切片:NFR-4]**

**NFR-4:仿真子进程在 Flask 退出时不能成为孤儿进程**。

解决方案是 **atexit 清理钩子**。这一条之所以重要,是因为子进程模型有一个**天然风险**——主进程崩了或被 Ctrl+C,子进程可能还在跑,继续占着 GPU 和内存。所以必须有兜底机制。**这是子进程架构的代价之一**——你享受了隔离,就要承担清理责任。

**[切片:NFR-13]**

**NFR-13:启动时若 3000 或 5001 端口被占用,必须强制 kill 占用进程,不允许更换端口**。

这条乍看很霸道,但背后是"**约定优于配置**"的思想——前端硬编码了 5001 作为后端地址,如果后端跑到别的端口,整个系统就连不上了。**与其让用户每次配置端口,不如把端口约定死**。这种"看似不灵活"的规则,反而降低了使用复杂度。

**[切片:NFR-15]**

**NFR-15:系统不引入数据库,全部状态以文件落盘**。

这是典型的 **YAGNI 原则**——You Aren't Gonna Need It。当前阶段单用户、单项目数,文件足以应付,引入数据库反而带来部署复杂度和运维成本。文档里特别加了一句"**引入数据库前必须先讨论**",这是在为未来升级留出**明确的决策点**——不是不做,是现在不做。

**[切片:NFR-11]**

**NFR-11:Windows 控制台必须保持 UTF-8 输出**。

这条看似琐碎,实际上是跨平台兼容的真实痛点——Windows 默认控制台是 GBK,Python 默认是 UTF-8,中文一打印就乱码。文档里特意点出"**backend/run.py 顶部的 UTF-8 设置代码块禁止删除**"。

**[强调]好的非功能性需求,要落到具体的代码位置,不能只写概念**。"系统应当支持中文"是废话,"backend/run.py 顶部的 UTF-8 设置代码块禁止删除"才是有效需求。

## 附录 A:可能的提问与应答准备

> 答辩前过一遍,临场会从容很多。

**Q1:为什么不直接用 Celery,自己写 TaskManager?**
A:Celery 需要 Broker(Redis 或 RabbitMQ),会让部署从"Python + Node"变成"Python + Node + Redis",对单机部署的小项目是过度工程。当前 TaskManager 是内存任务表 + daemon Thread,够用且无依赖。**未来如果上多用户并发,会重新评估**。

**Q2:文件 IPC 性能怎么样,会不会成为瓶颈?**
A:当前轮询间隔 200ms,采访这种交互场景延迟可接受。批量采访时确实可能堆积,这是 NFR-2 之外需要补充压测的方向。如果要扩展到大批量场景,会迁移到 socket 或 ZeroMQ。

**Q3:为什么不用数据库存项目和仿真状态?**
A:YAGNI——当前没有多用户、没有跨机查询需求,文件足够。文档 NFR-15 显式写了"引入数据库前必须先讨论",留了明确的升级决策点。

**Q4:OASIS 是什么?为什么选它?**
A:CAMEL-AI 团队开源的多智能体社会仿真框架,论文在 NeurIPS。选它的原因是它原生支持 Twitter / Reddit 双平台环境,而且智能体的行为是 LLM 驱动的,符合 MiroFish "用 LLM 模拟真实用户" 的需求。

**Q5:状态机里 FAILED 状态怎么恢复?**
A:每个 simulation_id / project_id 有独立目录,FAILED 状态可以重启对应步骤而不影响其他项目。这正是 NFR-3 "中途异常须可恢复"的落地方式。

**Q6:为什么子进程不在仿真结束后退出?**
A:为了支持 Interview——用户看完报告可能想问"为什么 Agent A 这么反应",这时候需要仿真环境还在,Agent 还能调用 LLM 回答。如果子进程退完了,就没法追问了。这是 UC6 后置条件"进入等待命令模式"的设计原因。
